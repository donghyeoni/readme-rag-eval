# 서비스 로그

측정 설정, 측정 결과, 설계 판단, 데이터, 서버 설정, 한계를 정리한다. README에는 동작과 사용 방법만 둔다.

## 1. 측정 설정

- **문항.** 50개(`eval/questions.jsonl`). 수치·목록 25개(`d1`–`d25`, DB로 답하는 문항)와 서술 25개(`s1`–`s25`,
  문서로 답하는 문항)다.
- **겨냥 문항과 홀드아웃.** 하네스 수정을 만들 때 실패를 본 20문항(`d1`–`d10`, `s1`–`s10`, `eval/compare.py`의
  `TARGETED`)과 나머지 30문항이다.
- **채점.** 답에 `must_include` 문자열이 모두 있으면 정답이다.
- **비교.** 같은 문항끼리 짝지은 McNemar 정확 검정(양측 이항)이다(`eval/compare.py`).
- **서빙.** 사내 GPU(L40S 1장)에 vLLM으로 Qwen2.5-7B / 14B-Instruct를 올렸다. 컨텍스트는 8192 토큰이다.
- 표의 정답률은 모두 조건 C(`search_docs`와 `query_db` 둘 다 사용)다.

## 3. 하네스 수정과 모델 확대가 바꾼 문항

| 변화 | 틀→맞 문항 | 맞→틀 문항 |
|---|---|---|
| 하네스 수정 (7B 고정, 수정 전 → 수정 후) | `d3 d20 d22 s1 s3 s4 s8 s9 s15` (9) | 3 |
| 모델 확대 (수정 고정, 7B → 14B) | `d1 d4 d9 d12 d16 d23 s2 s10 s18 s20` (10) | `d6 s1 s4 s6 s8` (5) |

- 두 변화의 틀→맞 문항은 겹치지 않는다.
- 모델 확대의 맞→틀 5문항 중 `s1 s4 s8`은 하네스 수정이 고친 문항이다.
- 모델 확대는 겨냥 20문항에서 0.650 → 0.650(틀→맞 5, 맞→틀 5, p=1.000), 홀드아웃 30문항에서 0.300 → 0.467
  (틀→맞 5, 맞→틀 0, p=0.062)이다.

## 4. 첫 수정 묶음의 문항별 결과 (7B)

첫 수정 묶음이 겨냥한 10문항 중 4문항이 틀→맞(`d3 s1 s4 s3`), 1문항이 맞→틀(`s10`)이고, 5문항은 계속
틀렸다(`d4 s2 d8 d9 d1`).

| 수정 | 대상 문항 | 결과 |
|---|---|---|
| `duration_days` 컬럼 추가 | `d3` | 틀→맞 |
| 표를 행 단위로 펴서 함께 주기 | `s1` | 틀→맞 |
| 도구 description 재작성 | `d4 s4 s10` | `s4` 틀→맞, `s10` 맞→틀 |
| 새어 나온 도구 호출 복구 | `s2 s3` | `s3` 틀→맞 (`s3`에서는 복구가 일어나지 않음) |
| 빈 결과에 "다시 조회하라" 힌트 | `d8 d9` | 둘 다 틀림 |
| 수치 검증기가 근거 없는 수치를 되묻기 | `d1` | 틀림 |

- `agent_C_fixed.csv`에서 호출 복구가 일어난 문항은 6개(`s2 s9 s12 s15 s19 s20`)이고, 그중 `s9`, `s15`가 정답이다.
- 검증기가 수치를 지적한 문항은 4개(`d9 d17 d24 s15`)이고, 그중 `d24`, `s15`가 정답이다.

## 5. 빈 결과 폴백 (14B)

`query_db` 결과가 0행이면 조건을 벗긴 `metrics` 행을 함께 돌려준다(`tools.py`의 `_fallback`). 같은 단계에서
`query_db`의 도구 설명도 고쳤다(`metrics.name` 전체 목록, DB에 없는 수치는 `search_docs`를 쓰라는 안내). 결과에는
DB에 있는 항목 목록(`db에_있는_것`)도 함께 붙인다. 아래 수치는 이 변경 전체의 결과다.

- 틀→맞 5문항(`d6 d11 d15 d18 d19`), 맞→틀 3문항(`d1 s3 s20`)으로 0.540 → 0.580이다.
- 50문항 평균 입력 토큰은 2,769 → 3,387이다. 틀→맞 5문항의 평균은 2,506 → 4,807이다.
- 검색 실패는 1 → 4건(`s3 s11 s13 s20`), 도구 선택 실패는 6 → 4건이다.
- `s13`은 14B에서 `query_db`를 골라 도구 선택 실패였고, 폴백 뒤에는 `search_docs`를 골라 검색 실패가 됐다.
  `s11`은 14B에서 도구를 부르지 않았고, 폴백 뒤에는 `search_docs`를 골라 검색 실패가 됐다.

## 6. 검색어 섞기 (14B)

`search_docs`가 모델의 검색어와 질문 원문으로 따로 찾은 결과를 번갈아 섞는다.

- 폴백 단계의 검색 실패 4건 중 3건(`s3 s11 s20`)은 질문 원문으로 검색하면 정답 문서가 상위 3개 안에 든다
  (`results/retrieval_expand-1.csv`).
- 섞기 뒤 0.580 → 0.600(틀→맞 2, 맞→틀 1)이다. 검색 실패는 4건(`s3 s11 s13 s18`)으로, `s20`이 빠지고
  `s18`이 새로 생겼다.

## 7. 버그 수정과 회귀

섞기 단계 측정 뒤 두 버그를 고쳤다.

1. 폴백이 붙인 행이 검색 결과와 겹치면 8192 토큰을 넘길 수 있었다. 섞기 단계에서 `s6`, `s25`가 컨텍스트
   초과(400)로 답을 받지 못했다(`s6`은 폴백을 넣기 전인 14B 측정부터 같은 오류였다).
2. 새어 나온 호출을 `tool_call` 태그가 있을 때만 복구해, 태그 없는 변종(`iNdEx {"name": ...}`)을 놓쳤다.

1번은 폴백 행을 글자 예산 안에서 자르고, 2번은 태그 없는 변종도 복구하도록 고쳤다. 두 수정을 넣고 다시 재자
0.600 → 0.500(틀→맞 0, 맞→틀 5: `d6 s2 d11 d18 d19`)이었다.

- 행을 레포 이름의 알파벳 순으로 잘라, 뒤쪽 레포의 행(`robust-image-classification` 일부,
  `tre-deepfake-detection`, `vanilla-rnn`, `yopar-attribute`)이 빠졌다. `metrics` 전체를 붙이는 경우 63행 중
  40행만 남는다. `d18`, `d19`는 "데이터가 없다"고
  답했고, `d11`은 틀린 값을 답했다.
- 이 측정에서 컨텍스트 초과로 답을 받지 못한 문항은 6개(`d6 s2 s6 s14 s17 s21`)이고, `d6`, `s2`는 직전
  측정에서 정답이었다.

다시 고쳤다. 원 쿼리의 낱말과 겹치는 행을 앞으로 올린 뒤 자르고, 컨텍스트 초과가 나면 오래된 도구 결과를 줄여
한 번 더 보낸다. 결과는 0.620(버그 수정 1차 대비 틀→맞 6, 맞→틀 0, p=0.031)이다.

Recall@3은 모두 같고, B의 `d1`(두 번 다 오답)에서 호출 수만 4회와 5회로 달랐다.

## 14. 설계 판단

**도구를 문서 검색과 SQL로 나눈 이유.** 서술형 질문("왜 이 필터를 골랐나")에는 문단이, 집계 질문("PSNR이
30dB를 넘는 프로젝트를 전부")에는 정렬 가능한 행이 필요하다. 도구 구성 A(검색만) / B(SQL만) / C(둘 다)를 같은
50문항에 돌려 비교했다(9절).

**한글 토큰화를 2-gram으로 한 이유.** 형태소 분석기는 외부 의존성과 설치 실패 지점을 늘린다. 2-gram은 추가 설치
없이 동작하고, `PSNR`·`Q1.15` 같은 짧은 기술 용어를 쪼개지 않는다.

**한→영 질의 확장을 붙인 이유.** 검색 대상 README 다수가 영어이고, BM25는 어휘 일치만 본다. "초해상도"로는
"super-resolution"이 걸리지 않는다. 임베딩 대신 손으로 쓴 표를 고른 이유는 항목 수가 적고, 무엇이 왜 걸렸는지
한 줄로 설명되기 때문이다.

**LLM이 생성한 SQL을 막는 방법.** 두 겹이다.

1. `SELECT`로 시작하지 않거나 쓰기 키워드(`insert|update|delete|drop|...`)가 보이면 거절하고, 세미콜론으로 문을
   이어 붙이는 것도 막는다.
2. 연결 자체를 읽기 전용으로 연다 — `sqlite3.connect("file:meta.db?mode=ro", uri=True)`.

1번은 통과하지만 의도와 다른 SELECT(예: `UNION`으로 상수 행 붙이기)는 여전히 가능해서, 연결 수준에서 한 겹 더
둔다.

**루프를 직접 쓴 이유.** SDK의 `tool_runner`가 루프를 대신 돌려주지만, 측정하려는 대상(어떤 도구를 먼저
불렀나, 몇 번 불렀나, 도구가 몇 번 실패했나)이 루프 안에 있다. 직접 들고 있어야 `Trace`로 뽑을 수 있다.
루프에서 지키는 규칙은 세 가지다.

1. `tool_result`의 `tool_use_id`는 해당 `tool_use`의 `id`와 같아야 한다.
2. 한 응답에 `tool_use`가 여러 개 오면 모든 `tool_result`를 하나의 메시지에 담는다. OpenAI 호환 쪽은 반대로
   도구마다 `role: "tool"` 메시지를 따로 보낸다 — `backends.py`가 이 차이를 흡수한다.
3. 실패한 도구도 결과를 빼먹지 않고 돌려준다. Anthropic 형식은 `is_error`를 붙이고, OpenAI 호환 형식에는 이
   필드가 없어 `ERROR:`로 시작하는 결과 문자열만 보낸다.

## 16. 온프레미스 GPU 서버 설정

사내 GPU 서버(L40S ×4, JupyterHub만 열려 있고 SSH는 없음)에 vLLM을 올렸다. `scripts/serve_vllm.py`가
JupyterHub 커널 WebSocket으로 원격 명령을 보낸다.

- 공용 파이썬(`/opt/tljh/user`)은 다른 사용자가 함께 쓰므로, 홈에 venv를 따로 만들어 설치했다.
- GPU는 비어 있던 0번을 썼다. 1번은 다른 작업이 41GB를 쓰고 있었다.

**vLLM 버전.** `pip install vllm`으로 최신판(0.29.0)을 깔면 `torch 2.13.0+cu130`이 따라오는데, 이 서버
드라이버는 `570.211.01`(CUDA 12.8)이라 엔진이 뜨지 않는다:

```
RuntimeError: The NVIDIA driver on your system is too old (found version 12080)
```

vLLM 휠은 파일명에 CUDA 버전이 없어서, 각 vLLM이 고정한 torch의 PyPI 기본 CUDA로 거꾸로 판별했다.

| vLLM | 고정 torch | torch의 PyPI 기본 CUDA | 이 드라이버에서 |
|---|---|---|---|
| 0.27 ~ 0.29 | 2.13.0 | cu130 | X |
| 0.20 ~ 0.26 | 2.11.0 | cu13x | X |
| **0.17 ~ 0.19** | **2.10.0** | **`nvidia-cuda-runtime-cu12==12.8.90`** | **O** |

그래서 `vllm==0.19.1`로 고정했다. `torch`만 cu128로 내리는 방법은 vLLM의 컴파일된 확장이 CUDA 13으로 빌드돼
있어(`libcudart.so.13`을 찾음) 동작하지 않는다. 제자리 다운그레이드는 이전 설치의 `nvidia-*-cu13` 패키지가
남아 섞이므로 venv를 새로 만들었다. 드라이버는 공용 서버라 건드리지 않았다.
