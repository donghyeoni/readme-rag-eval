# readme-rag-eval

내 프로젝트 문서 12건을 검색하고 SQLite에 질의해 답하는, 도구 연동형 LLM 시스템.
**질문 50개에 정답을 라벨링해 검색·도구 선택·생성 정확도를 따로 측정했고,
하네스 수정과 모델 확대 중 무엇이 무엇을 고쳤는지 같은 문항 위에서 갈랐다.**

구현만으로는 "LLM을 붙여 봤다"에서 끝난다. 이 저장소의 내용은 무엇이 얼마나
맞았고, 틀린 것이 **어디서** 틀렸는지를 나눈 표다.

## 결과

문항 50개(수치·목록 25 / 서술 25)에 정답을 라벨링하고, **같은 문항 위에서**
하네스 수정 전후와 모델 크기를 비교했다. 온프레미스 GPU(L40S 1장)에 vLLM으로
서빙했다.

### 무엇이 정확도를 올렸나

| 조건 C (도구 둘 다) | 수정이 겨냥한 20문항 | 홀드아웃 30문항 | 전체 50문항 |
|---|---|---|---|
| 수정 전 · Qwen2.5-7B | 0.450 | 0.233 | 0.320 |
| 수정 후 · Qwen2.5-7B | **0.650** | 0.300 | 0.440 |
| 수정 후 · Qwen2.5-14B | 0.650 | **0.467** | **0.540** |

**홀드아웃을 나눈 이유** — 하네스 수정 6가지는 전부 앞선 20문항의 실패를 보고
만들었다. 나머지 30문항은 README 내용만 보고 썼고 실패 분석을 참고하지 않았다.
그래서 30문항은 이 수정들에 대해 사실상 홀드아웃이다. 이걸 나누지 않으면
"내가 만든 문제로 내가 고쳐 가며 잰 숫자"와 구분되지 않는다.

### 하네스와 모델은 서로 다른 문항을 고쳤다

**고친 문항이 하나도 겹치지 않는다.**

| | 고친 문항 수 | 어느 문항 |
|---|---|---|
| 하네스 수정 (7B 고정) | 9 | `d3 d20 d22 s1 s3 s4 s8 s9 s15` |
| 모델 확대 (수정 고정) | 10 | `d1 d4 d9 d12 d16 d23 s2 s10 s18 s20` |
| **겹침** | **0** | — |

겨냥한 20문항에서 14B는 **아무것도 더 못 얻었다**(0.650 → 0.650, 뒤집힘 5:5,
p=1.000). 하네스가 이미 손본 자리에는 모델을 키워도 남는 게 없었고, 손대지 않은
홀드아웃에서만 올랐다(+0.167, 뒤집힘 5:0, p=0.062).

즉 **"하네스냐 모델이냐"는 잘못된 질문**이다. 둘은 다른 종류의 실패를 고친다.

### 그런데 어느 쪽도 통계적으로 확립되지 않았다

같은 문항을 두 조건으로 돌렸으므로 짝지은 검정(McNemar)이 맞다.

| 비교 | 차이 | 틀→맞 | 맞→틀 | p |
|---|---|---|---|---|
| 수정 전 → 수정 후 (7B) | +0.120 | 9 | 3 | 0.146 |
| 7B → 14B (수정 후) | +0.100 | 10 | 5 | 0.302 |
| 7B → 14B, 홀드아웃만 | +0.167 | 5 | 0 | **0.062** |

**p < 0.05인 칸이 없다.** 방향은 일관되지만 뒤집힌 문항이 적어 우연으로도
설명된다. 50문항에서 표준오차가 ±3.5문항이라, 6문항 순증으로는 모자란다.
그래서 이 저장소는 **"고쳐서 좋아졌다"고 주장하지 않는다.** 홀드아웃 5:0 한
칸만 경향으로 읽을 만하다.

### 도구 구성 ablation

| 모델 | 조건 | 도구 | Recall@3 | 정답률 | 도구 선택 | 평균 호출 | 에러율 | 지연 |
|---|---|---|---|---|---|---|---|---|
| 7B | C | 둘 다 | 0.375 | 0.440 | 0.860 | 1.1 | 0.070 | 5.2s |
| 7B | A | 검색만 | 0.675 | 0.340 | 0.800 | 0.9 | 0.070 | 6.1s |
| 7B | B | SQL만 | -- | 0.220 | (1.000) | 1.0 | 0.188 | 3.8s |
| 14B | C | 둘 다 | 0.425 | **0.540** | 0.800 | 1.2 | 0.048 | 8.2s |
| 14B | A | 검색만 | 0.700 | 0.420 | 0.920 | 0.9 | 0.070 | 10.8s |
| 14B | B | SQL만 | -- | 0.300 | (1.000) | 1.2 | 0.034 | 8.9s |

B의 도구 선택 정확도 1.000은 고를 도구가 하나뿐이라 자동으로 1이다. 지표가 아니다.

**도구를 둘로 나눈 가설은 이번엔 두 모델 모두에서 지지된다.** C가 A보다 7B에서
+5문항, 14B에서 +6문항 앞선다. 20문항일 때는 1문항 차이라 말할 수 없었는데,
문항을 50개로 늘리자 갈렸다. A의 "도구 구성 한계" 8~14건은 검색만으로는 닿지
않는 집계 질문이고, B의 13~23건은 문서를 봐야 하는 서술형이다.

### 고친 것과 그 결과 — 10건 중 4건

수정 6가지는 전부 실패 분석이 지목한 곳을 겨냥했다. 겨냥한 10문항의 결산:

| 수정 | 성격 | 겨냥 | 고쳐짐 |
|---|---|---|---|
| `duration_days` 컬럼 | 자료의 모양 | d3 | **O** |
| 표를 행 단위로 펴서 전달 | 자료의 모양 | s1 | **O** |
| 도구 description 재작성 | 지시 | d4 s4 s10 | 1/3 (s10은 망가짐) |
| 새어 나온 도구 호출 복구 | 기회 부여 | s2 s3 | 1/2 |
| 빈 결과에 재조회 힌트 | 기회 부여 | d8 d9 | 0/2 |
| 수치 검증기 (되묻기) | 기회 부여 | d1 | 0/1 |

읽히는 것은 이것이다:

- **자료의 모양을 바꾼 수정은 2/2로 전환됐다.** 같은 모델에 같은 정보를 주되
  표현만 바꿨더니 답이 맞았다.
- **모델에게 기회를 더 주는 수정은 거의 전환되지 않았다(1/5).** 메커니즘은
  작동했다 — 새어 나온 호출을 6건 복구했고 검증기가 수치를 4건 지적했다.
  그런데 **복구해서 다시 물어도 모델은 같은 실수를 했다.**

특히 빈 결과 힌트가 그렇다. `query_db`가 0행일 때 "포기하지 말고 조건을 넓혀
다시 조회하세요"를 결과에 실어 보냈는데, 14B조차 그 문장을 읽고 **"조건에 맞는
결과가 없습니다"라고 답하며 끝냈다.** 지시를 자료에 적어 주는 것으로는 부족하고,
루프가 재시도를 **강제**해야 한다는 뜻이다. 다음 실험의 출발점이다.

### 세 조건 모두 못 고친 17문항

| 유형 | 건수 |
|---|---|
| 생성 실패 | 9 |
| 도구 선택 실패 | 6 |
| 도구 미사용 | 1 |
| 검색 실패 | 1 |

생성 실패 9건은 거의 전부 **DB에서 값을 찾아 그대로 옮기는 질문**이다. 모델이
쿼리를 한 번 날리고, 빗나가면 포기하거나(d15, d18) 절반만 답한다(d17: 16-QAM은
찾고 QPSK는 "없다"). 검색기 문제도, 도구 문제도 아니다.

### 앞선 측정에서 이미 얻은 것

**프롬프트 한 문장이 도구 호출을 통째로 없앴다.** 처음 시스템 프롬프트에 넣은
`"도구로 확인되지 않으면 모른다고 답하라"`를 7B는 **도구를 부르기 전에** 모른다고
해도 된다는 허가로 읽었다. 문장을 하나씩 붙여 가며 도구 호출을 셌다(각 5문항):

| 시스템 프롬프트 | 도구 호출 |
|---|---|
| 역할만 | 5/5 |
| + 근거 인용 지시 | 5/5 |
| + **"확인되지 않으면 모른다고 답하라"** | 1/5 |
| + 수치 보존 지시 (= v0 전체) | 0/5 |
| 역할 + 근거 + 수치 (문제 문장만 제거) | 5/5 |
| **v2: "도구를 한 번도 부르지 않은 채로 모른다고 답해서는 안 된다"** | **5/5** |

20문항 기준으로 **도구 미사용이 8건에서 2건으로** 줄었다. 정답률도 0.350에서
0.450이 됐지만 20문항에서 2문항 차이라 그것만으로는 개선이라 말하지 않는다.
**측정하지 않았다면 "7B는 도구를 잘 못 쓴다"는 틀린 결론을 냈을 것이다.**

**한국어 질문이 영어 문서를 못 찾았다.** 문서 12건 중 9건이 영어 README라
"초해상도"로는 "super-resolution"이 걸리지 않는다. 손으로 쓴 별칭표로 질의를
확장했다(검색기 단독, 라벨 40문항):

| 질의 확장 | Recall@1 | Recall@3 | Recall@5 |
|---|---|---|---|
| off | 0.325 | 0.500 | 0.725 |
| **on** | **0.650** | **0.975** | **1.000** |

놓친 1건(`s13`)은 한국어 문서가 영어 문서를 밀어낸 경우다. 별칭표에 단어를
더하면 고칠 수 있지만 하지 않았다 — 실패를 본 뒤 그 문항이 걸리도록 표를
늘리는 것은 평가셋에 맞추는 일이다.

### 로컬 GPU 비교

| | Qwen2.5-7B | Qwen2.5-14B |
|---|---|---|
| 정답률 (조건 C, 50문항) | 0.440 | 0.540 |
| 질문당 지연 | 5.2s | 8.2s |
| 50문항 토큰 | 입력 144,151 / 출력 12,302 | 입력 138,469 / 출력 10,054 |
| 금전 비용 | 없음 (사내 GPU) | 없음 (사내 GPU) |

둘 다 L40S 한 장에 올라간다. **정확도 +0.10을 지연 1.6배로 산다.** 사내에서
"어느 작업까지 작은 모델로 내려도 되는가"를 정할 때 필요한 형태의 표다.
다만 위에서 적었듯 이 +0.10은 p=0.302로, 확립된 차이가 아니다.

Anthropic API 행은 비어 있다 — 이 PC에 API 키가 없고 API는 유료라 키 없이
돌릴 수 있는 로컬 트랙만 측정했다. `agent.py --backend anthropic` 경로는
구현돼 있고 `backends.py`가 두 형식의 차이를 흡수한다.

### 재현성

같은 설정으로 4회 반복했을 때 20문항의 정답/오답, 첫 호출 도구, Recall@3이
전부 같았다. 다만 이미 오답이던 한 문항에서 재시도 횟수만 4회와 5회로 갈렸고,
더 이른 실행 한 번은 2문항이 달랐다. 완전한 재현성을 주장하지 않고 **측정
해상도를 ±1~2문항으로 본다.**

## 무엇을 만들었나

```
질문
 +-> [LLM 루프] --- tool_use ---> search_docs(query, k) --> docs/*.md 청크 BM25 상위 k개
       ^                     +--> query_db(sql)          --> SQLite (repos, metrics)
       |                                                        |
       +----------------- tool_result <-------------------------+

 최종 답변 = 텍스트 + 인용한 문단/행
```

| 파일 | 역할 |
|---|---|
| [`retriever.py`](retriever.py) | 마크다운 헤딩 단위 청킹 + BM25. 한글 2-gram 토큰화 |
| [`aliases.py`](aliases.py) | 한국어 질문 → 영어 문서를 잇는 질의 확장표 |
| [`build_db.py`](build_db.py) | `repos` / `metrics` 두 테이블 적재 (수치는 손으로 옮김) |
| [`tools.py`](tools.py) | `search_docs` / `query_db` 구현과 도구 스키마 |
| [`backends.py`](backends.py) | Anthropic API와 OpenAI 호환(vLLM)을 한 인터페이스 뒤에 |
| [`agent.py`](agent.py) | `stop_reason`을 보며 직접 도는 도구 호출 루프 |
| [`verifier.py`](verifier.py) | 답의 수치가 도구 출력에 있는지 대조 |
| [`eval/`](eval/) | 라벨 50문항, 측정·비교·라벨검증 스크립트 |
| [`scripts/serve_vllm.py`](scripts/serve_vllm.py) | JupyterHub 커널로 온프레미스 GPU에 vLLM 기동 |

## 설계 판단

### 1. 도구를 문서 검색과 SQL로 나눈 이유

서술형 질문("왜 이 필터를 골랐나")과 집계 질문("PSNR이 30dB를 넘는 프로젝트를
전부")은 필요한 자료구조가 다르다. 전자는 문단이, 후자는 정렬 가능한 행이 있어야
한다. 한쪽으로만 만들면 반대쪽 질문에서 무너진다 — 라는 것이 **가설**이었고,
도구 구성 A(검색만) / B(SQL만) / C(둘 다)를 같은 50문항에 돌려 확인했다.
20문항일 때는 C와 A가 1문항 차이라 결론을 낼 수 없었고, 50문항으로 늘리자
두 모델 모두에서 C가 A보다 5~6문항 앞섰다.

### 2. 한글 토큰화를 2-gram으로 한 이유

형태소 분석기는 외부 의존성과 설치 실패 지점을 늘린다. 2-gram은 `pip install`
없이 재현되고, `PSNR`·`Q1.15` 같은 짧은 기술 용어에서 오히려 안전하다.

### 3. 한→영 질의 확장을 붙인 이유 (계획에 없던 것)

문서 12건 중 **9건이 영어 README**다. BM25는 어휘 일치만 보므로 "초해상도"로는
"super-resolution"이 한 건도 걸리지 않는다. 계획 단계에서는 몰랐고, 검색기를
단독으로 측정하자마자 드러났다.

| 질의 확장 | Recall@1 | Recall@3 | Recall@5 |
|---|---|---|---|
| off | 0.325 | 0.500 | 0.725 |
| **on** | **0.650** | **0.975** | **1.000** |

라벨이 붙은 40문항 기준 (`python eval/run_eval.py --retrieval-only`).
임베딩 대신 손으로 쓴 58항목 표를 고른 이유는 항목 수가 적고, 무엇이 왜 걸렸는지
한 줄로 설명되기 때문이다.

### 4. LLM이 생성한 SQL을 어떻게 막았나

두 겹이다.

1. `SELECT`로 시작하지 않거나 쓰기 키워드(`insert|update|delete|drop|...`)가
   보이면 거절하고, 세미콜론으로 문을 이어 붙이는 것도 막는다.
2. 연결 자체를 읽기 전용으로 연다 — `sqlite3.connect("file:meta.db?mode=ro", uri=True)`.

**실제 방어선은 2번이다.** 1번은 통과하지만 의도와 다른 SELECT(예: `UNION`으로
상수 행 붙이기)는 여전히 가능하고, 실제로 통과하는 것을 확인했다. 문자열 검사만으로
막았다고 말할 수 없어서 연결 수준에서 한 겹 더 둔 것이다.

### 5. 루프를 직접 쓴 이유

SDK의 `tool_runner`가 대신 돌려주지만, 이 프로젝트에서 측정하려는 대상이
루프 안에서 오가는 것(어떤 도구를 먼저 불렀나, 몇 번 불렀나, 도구가 몇 번
실패했나)이다. 직접 들고 있어야 `Trace`로 뽑을 수 있다.

루프에서 실제로 틀리기 쉬운 곳 세 가지:

1. `tool_result`의 `tool_use_id`는 해당 `tool_use`의 `id`와 정확히 같아야 한다.
2. 한 응답에 `tool_use`가 여러 개 오면 **모든** `tool_result`를 **하나의** 메시지에
   담는다. 쪼개 보내면 모델이 병렬 호출을 그만둔다. (OpenAI 호환 쪽은 반대로
   도구마다 `role: "tool"` 메시지를 따로 보낸다 — `backends.py`가 이 차이를 흡수한다.)
3. 실패한 도구도 결과를 빼먹지 않고 `is_error`로 돌려준다.

메타DB. README 파싱을 자동화하지 않은 이유는 12개뿐이고 표 형식이 제각각이라
파서가 조용히 틀리기 때문이다.

**`docs/*.md`는 이 저장소에 넣지 않는다.** 원본이 각 레포에 이미 공개돼 있는 사본이라
두 곳에서 갈라지기 때문이다. 대신 `python scripts/fetch_docs.py`(내부적으로
`gh api repos/<user>/<repo>/readme`)로 언제든 같은 상태를 만든다 — 측정에 쓴 12건과
바이트 단위로 같은 파일을 받는 것을 확인했다.

- 청크 110개 / 11개 레포 (`Algorithm-training`은 README가 한 줄이라 청크가 없다 —
  DB에는 있고 문서 검색에는 없는 레포가 하나 생긴다)
- `repos` 12행, `metrics` 63행

```sql
repos(name, language, domain, started, ended, summary)
metrics(repo, name, condition, baseline, value, unit)
```

## 사용법

```bash
pip install -r requirements.txt
python scripts/fetch_docs.py   # 검색 대상 README 12건 수집 (gh CLI 필요)
python build_db.py
```

검색기만 확인 (LLM 불필요):

```bash
python retriever.py "초해상도 중요도 맵"
python eval/run_eval.py --retrieval-only
```

질문 하나 던지기:

```bash

```

전체 평가 (도구 구성 A/B/C):

```bash
python eval/run_eval.py --backend vllm:http://localhost:8000 --toolsets A,B,C
```

## 온프레미스 GPU 트랙

사내 GPU 서버(L40S ×4, JupyterHub만 열려 있고 SSH는 없음)에 vLLM을 올려 같은
평가를 돌렸다. `scripts/serve_vllm.py`가 JupyterHub 커널 WebSocket으로 원격
명령을 보낸다.

```bash
export JUP_HOST=... JUP_USER=... JUP_TOKEN=...
python scripts/serve_vllm.py gpus      # 빈 GPU 확인
python scripts/serve_vllm.py setup     # 홈에 전용 venv 만들고 vLLM 설치
python scripts/serve_vllm.py up --gpu 0
python scripts/serve_vllm.py status
```

공용 파이썬(`/opt/tljh/user`)에 설치하지 않고 홈에 venv를 따로 판 이유는 그
인터프리터를 다른 사용자가 함께 쓰기 때문이다. GPU도 비어 있는 장치(0번)만 골라
썼다 — 1번은 다른 작업이 41GB를 쓰고 있었다.

### 버전 고르기 — 드라이버가 상한을 정한다

`pip install vllm`으로 최신판(0.29.0)을 깔면 `torch 2.13.0+cu130`이 따라오는데,
이 서버 드라이버는 `570.211.01`(CUDA 12.8)이라 엔진이 뜨지 않는다:

```
RuntimeError: The NVIDIA driver on your system is too old (found version 12080)
```

vLLM 휠은 파일명에 CUDA 버전이 없어서, **각 vLLM이 고정한 torch의 PyPI 기본 CUDA**로
거꾸로 판별했다.

| vLLM | 고정 torch | torch의 PyPI 기본 CUDA | 이 드라이버에서 |
|---|---|---|---|
| 0.27 ~ 0.29 | 2.13.0 | cu130 | X |
| 0.20 ~ 0.26 | 2.11.0 | cu13x | X |
| **0.17 ~ 0.19** | **2.10.0** | **`nvidia-cuda-runtime-cu12==12.8.90`** | **O** |

그래서 `vllm==0.19.1`로 고정했다. 중간에 `torch`만 cu128로 내려도 안 되는데,
**vLLM의 컴파일된 확장 자체가 CUDA 13으로 빌드**돼 있어 `libcudart.so.13`을 찾기
때문이다. 또 제자리 다운그레이드는 이전 설치의 `nvidia-*-cu13` 패키지가 남아
섞이므로, venv를 지우고 새로 만드는 편이 빠르다.

드라이버를 올리는 선택지는 공용 서버라 건드리지 않았다.
